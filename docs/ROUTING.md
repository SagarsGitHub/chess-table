# Carried-piece routing

The computer-side route planner represents the 8×8 board on an integer half-square grid. Square centers are odd/odd: `a1=(1,1)` and `h8=(15,15)`. The 32 parking slots are even/even intersections around the perimeter, using the mapping in `firmware/include/BoardCoordinates.h`. A route includes pickup and delivery points.

The planner connects a square center diagonally to a neighboring grid intersection, travels along horizontal, vertical, or 45-degree grid lines, and enters the destination square diagonally. It may use a vacant edge-square center to reach a corner slot blocked by occupied adjacent parking slots. It avoids passing through occupied centers and occupied parking slots. Straight grid runs are compressed into turn points; every diagonal endpoint is retained so the Uno accepts the segment. If a preferred path exceeds the waypoint cap, the planner searches for another route with fewer turns before failing explicitly.

Physical runs showed that a long horizontal passage between standing pieces can disturb neighbors that are slightly off-center. The route search therefore adds a cumulative risk cost on horizontal grid edges beside occupied board squares: a neighbor on one side adds roughly one grid-edge length of cost, while neighbors on both sides add roughly five. This makes an open detour preferable to a long crowded corridor, even if it is geometrically longer. The cost is a route preference; the measured-clearance check and offset preflight decide whether a selected passage can actually be used.

`plan_transfer_route()` works from the occupancy snapshot **before one transfer**. After a capture victim is parked, the caller must update square and slot occupancy before routing the attacking piece. `find_reachable_parking_slot()` tries vacant slots in order; `ReachableParkingSlotSelector` integrates that search with the logical move planner, including capture-promotion sequences. If the first directly reachable slot does not yield a complete strict capture plan, the game runner checks the remaining vacant slots with full move preflight before considering a tight route.

For a board move or capture leg with no measured-clearance route, the host searches for one occupied board square whose removal opens the intended carry. It tries a vacant board square and then parking as a temporary destination, carries the intended piece, and restores the blocker. All three legs must pass measured clearance against their successive occupancy snapshots and fit the 12-waypoint cap. This search applies at any game position and to board-to-parking capture legs. A knight move is rejected if neither staging nor offset search finds a complete checked plan. In the full starting position, the software plan for `b1c3` is `b2→b3`, `b1→c3`, `b3→b2`; the three mirrored knight openings have matching plans.

When moving a blocker out of its square is unnecessary or impossible, the host searches a bounded within-square alternative. It identifies neighbors beside a candidate tight carry, tries moving one or two of them 0.30 square pitch toward corners using `OFFSET OUT`, plans the intended `CARRY` with measured clearance from their displaced positions, then checks the reverse `OFFSET IN` actions. The neighbor remains assigned to its original square in the board and controller maps. Each nudge, carry, and restoration must fit measured travel and clearance limits; the entire bundle is checked before its first command and each action gets its own checkpoint. This search also runs during board reset. It cannot clear every corridor: if the bounded search finds no complete checked plan, the host rejects a modeled clearance violation before motion.

Castling first nudges the original rook 0.30 square pitch toward a corner **within its own square** using `OFFSET OUT`; the host keeps that square occupied and does not claim a parking slot. It tries both outer-file corners in a three-action plan before considering temporary staging. The king is carried while the rook is offset, then `CARRY_OFFSET` picks the rook up at that corner and takes it directly to its castled square. When nearby pieces block the final rook carry, the host tries a single nearby friendly-piece stage and then a bounded pair, restoring each after the rook carry. In the tested full-pawn-rank white kingside position, the plan is `g2→g3`, `h1 OFFSET NE OUT`, `e1→g1`, `h1 CARRY_OFFSET NE →f1`, `g3→g2`. Each staged or offset action is preflighted with measured clearance, and every action is checkpointed separately. The king carry is checked against both the rook's nominal square center and its offset point; the final rook route is measured from the offset point. If every checked plan fails and tight routes are enabled, a last-resort three-action plan keeps the rook nudge while allowing the king and rook carries to pass closer to standing pieces than the configured circular clearance. It still checks occupied-center crossings, measured bounds, the 12-waypoint cap, the offset pickup leg, and compensated release clearance before motion. A saved older king-first or parking-slot castling plan needs inspection before resuming. These checks use expected piece positions and cannot detect a piece shifted by earlier motion.

Without measured `RouteGeometry`, a path is only a topological candidate. Checked routing requires the X/Y travel spans, end inset, pulses-per-mm scale, board pitch, moving and stationary piece diameters, and a clearance margin. Supply the current board origins too, especially after referencing saved geometry. Read these machine values from the framed `GEOM` command after `HOME` or `REF`. The planner maps every waypoint, offset endpoint, and magnet-release extension through the measured firmware coordinates and pulse rounding, then checks circular center distance in millimeters. This matters because a clamped perimeter run can be closer to first-rank pieces than its ideal grid line. `GEOM` rounds values to four decimals, so the margin must also account for that and for path tracking and physical centering error. The model still does not account for magnet coupling, piece wobble, board misalignment, or neighboring pieces being displaced by earlier motion. Inspect neighboring pieces on newly tested loaded routes.

For a board-square delivery by `CARRY` or `CARRY_OFFSET`, the loaded magnet continues past the nominal center along the final incoming segment before releasing. `OFFSET OUT` and `OFFSET IN` use the same extension beyond their nominal corner or center. The first candidate is **0.20 square pitch** (6.25 mm at the current 31.25 mm pitch). If that release pulse target exceeds measured travel bounds, host and firmware try 90% of the extension (5.625 mm); if both exceed bounds, preflight rejects the action. The host selects the same attempt as firmware, then applies a further 0.05 mm bound guard for `GEOM` rounding; a near-limit target can therefore be rejected rather than silently shortened. A `CARRY` to perimeter parking stops and releases at the parking slot. The extra travel is not an encoded waypoint: route endpoints, expected occupancy, and offset bookkeeping still name the nominal square or corner. The host checks the extended loaded segment against measured travel bounds, nominal obstacles, and any known displaced pieces. Firmware checks release pulse bounds and at least 18 mm clearance from occupied centers in its nominal `MAP` along the extra segment, as well as checking the encoded route. The host also checks displaced-piece positions and its configured clearance margin. A route may therefore fail even when its encoded waypoints fit. This is a delivery compensation for expected piece lag, not a measurement of the piece's final position. Verify where the piece actually stops during loaded trials.

For ordinary carries, the host first tries measured circular clearance with the risk-weighted route preference, then searches for a strict blocker stage and a complete offset bundle. If `allow_tight_routes` is enabled, an ordinary final candidate route may be checked, but it is rejected whenever it violates modeled piece clearance. Knight moves do not use that retry. Castling has its own last-resort override after every checked castle plan fails; only intermediate carry-segment circular clearance is relaxed. Measured travel bounds, occupied-center crossings, route topology, and the Uno's 12-waypoint capacity always apply. `--strict-clearance` disables the retry for a session. This model still cannot certify that a physically displaced neighbor will not be bumped.

The host tests cover all 4,032 distinct square pairs and all 64×32 square/parking pairs in both directions with empty perimeter storage. Every nominal route in this matrix fits the Uno's 12-point `CARRY` command and passes its segment-shape rules. A more obstructed route can exceed 12 points; the host then searches for a lower-turn route and rejects it if none fits. This test evidence proves the software topology and encoding, not that the board can physically carry each piece.
