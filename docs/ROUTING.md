# Carried-piece routing

The computer-side route planner represents the 8×8 board on an integer half-square grid. Square centers are odd/odd: `a1=(1,1)` and `h8=(15,15)`. The 32 parking slots are even/even intersections around the perimeter, using the mapping in `firmware/include/BoardCoordinates.h`. A route includes pickup and delivery points.

The planner connects a square center diagonally to a neighboring grid intersection, travels along horizontal, vertical, or 45-degree grid lines, and enters the destination square diagonally. It may use a vacant edge-square center to reach a corner slot blocked by occupied adjacent parking slots. It avoids passing through occupied centers and occupied parking slots. Straight grid runs are compressed into turn points; every diagonal endpoint is retained so the Uno accepts the segment. If a preferred path exceeds the waypoint cap, the planner searches for another route with fewer turns before failing explicitly.

Physical runs showed that a long horizontal passage between standing pieces can disturb neighbors that are slightly off-center. The route search therefore adds a cumulative risk cost on horizontal grid edges beside occupied board squares: a neighbor on one side adds roughly one grid-edge length of cost, while neighbors on both sides add roughly five. This makes an open detour or a short squeeze preferable to a long crowded corridor, even if it is geometrically longer. The penalty is a preference, not a ban; a crowded path may still be selected when other routes are unavailable or costlier. It does not move neighboring pieces.

Replanning the logged `h3` to `c1` occupancy from `computer/runs/gui-physical-20261005-163108.serial.jsonl` with 18 mm moving/standing diameters and tight-route fallback replaces a 93.75 mm two-sided horizontal passage with a six-waypoint detour containing no two-sided horizontal edge. Strict clearance finds no route in that position. This is software evidence; the detour has not yet been tried on the table.

`plan_transfer_route()` works from the occupancy snapshot **before one transfer**. After a capture victim is parked, the caller must update square and slot occupancy before routing the attacking piece. `find_reachable_parking_slot()` tries vacant slots in order; `ReachableParkingSlotSelector` integrates that search with the logical move planner, including capture-promotion sequences.

Without measured `RouteGeometry`, a path is only a topological candidate. Checked routing requires the X/Y travel spans, end inset, pulses-per-mm scale, board pitch, moving and stationary piece diameters, and a clearance margin. Supply the current board origins too, especially after referencing saved geometry. Read these machine values from the framed `GEOM` command after `HOME` or `REF`. The planner maps every waypoint through the same perimeter clamp and pulse rounding used by the firmware, then applies a circular center-distance check in millimeters. This matters because a clamped perimeter run can be closer to first-rank pieces than its ideal grid line. `GEOM` rounds values to four decimals, so the margin must also account for that and for path tracking and physical centering error. The model still does not account for magnet coupling, piece wobble, board misalignment, or neighboring pieces being displaced. Inspect neighboring pieces on newly tested loaded routes.

For this table, `allow_tight_routes` first tries the measured circular clearance with the risk-weighted route preference. If that fails, the host can retry without the piece-footprint distance check, while retaining the same route preference. The retry still checks measured travel bounds, occupied-center crossings, route topology, and the Uno's 12-waypoint capacity. The CLI prints `CLEARANCE OVERRIDE` for a transfer that uses the retry, and `--strict-clearance` disables it for a session. The override is a routing choice based on reported physical experience; it does not certify that nearby pieces cannot be bumped.

The host tests cover all 4,032 distinct square pairs and all 64×32 square/parking pairs in both directions with empty perimeter storage. Every nominal route in this matrix fits the Uno's 12-point `CARRY` command and passes its segment-shape rules. A more obstructed route can exceed 12 points; the host then searches for a lower-turn route and rejects it if none fits. This test evidence proves the software topology and encoding, not that the board can physically carry each piece.
