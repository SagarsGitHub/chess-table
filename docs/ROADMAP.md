# Roadmap

The target is a chess table that can complete a full game, park captured pieces around the perimeter, and recover predictably from interrupted motion. A stage is complete only when its acceptance evidence is recorded in this repository.

**Current sequence:** Stage 1 magnet-release reset diagnosis remains deferred at the user's request. Stage 2 and the software/simulator portion of stage 3 are implemented. The empty-board test passed with `GEOM X=249.7350 Y=251.9850 OX=-0.1325 OY=0.9925 P=31.2500 I=2.0000 PPM=133.3333`. The user accepts the physical game-and-reset path and reports that recovery works well. The recorded GUI game reached a 126-ply draw with 20 parked pieces; its recovered reset left all 32 pieces home and parking empty. Longer physical runs work overall, but long horizontal carries between standing pieces can disturb them when they are off-center. The host now penalizes those routes heavily; physical validation of the new preference remains. A PTFE dry-lube trial did not help and is discontinued. Physical promotion, every parking slot, and interrupted-capture coverage are not yet established by the recorded evidence. During movement a limit closure must persist for 3 ms to stop motion; idle and between-segment switch activity is ignored. The table uses explicit human move entry and checkpointed expected occupancy; physical sensing is out of scope. Faults and uncertain outcomes still require physical reconciliation.

The pieces currently balance on a ferrite rod that protrudes slightly below each base. The PTFE dry-lube trial did not work well, so discontinue it. If friction work resumes, compare a thin low-friction skid over the contact point with a stable three-pad base on one piece. Measure sliding force with the magnet off and on, and observe coupling, rocking, neighboring displacement, and board marks before modifying the full set. Added pad thickness can reduce magnetic coupling by increasing the gap.

At the measured 31.25 mm pitch, two 18 mm standing pieces leave a nominal 13.25 mm gap for an 18 mm moving piece. Off-center neighbors reduce that gap further. Slowing a crowded horizontal carry reduces impact but cannot create clearance. The host heavily penalizes long horizontal passages between occupied neighbors when choosing a route, preferring an open detour or shorter exposed passage if one fits the existing safety and waypoint limits. Neighbor-relocation transfers would add motion and recovery state, so they remain an alternative only if route selection does not solve the interaction.

The host now adds cumulative risk cost to crowded horizontal edges. In a read-only replan of a logged `h3` to `c1` carry, the old route used a 93.75 mm horizontal leg between occupied neighbors; the new route uses six waypoints and no horizontal edge with neighbors on both sides. This is a software replan of the logged occupancy, not a physical trial of the new route.

## Full-game GUI

The GUI is a local front end to the checkpointed host runner. It uses the same legal-move, parking, routing, Stockfish, and serial code as the CLI; one session owns the Uno and the game-state file. It accepts explicit human moves because the table has no physical sensing. In normal play, a matched `DONE CARRY` advances the expected physical state without routine move-by-move confirmation. The user reports core loaded-game, reset, and recovery acceptance after physical play.

## Fixed promotion rule

There are no spare queens, rooks, bishops, or knights for promotion. The pawn remains the physical piece on the board while the rules engine and Stockfish use the selected promoted type. Later moves carry that same pawn; capture parks it as a pawn. The game runner does not swap in a parked piece or request a manual replacement. Record both the legal and physical identities in game checkpoints and operator-facing state.
