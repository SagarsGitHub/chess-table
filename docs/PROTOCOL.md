# Serial protocol

The integration firmware uses a versioned, newline-terminated ASCII link at **115200 baud**. The computer must use framed mode and must never infer success from a delay or from a printed waypoint. Each host request, including its newline, is at most 96 bytes. The host accepts up to 128 bytes before the newline in controller replies so extended capability lists fit.

## Version 1 frame contract

The computer sends `@<id> <VERB> [arguments]\n`, where `<id>` is a positive decimal request ID. Only one normal request may be active; `STOP` can preempt a motion or reference operation. The firmware responds with `@<id> ACK` when it accepts a request and later emits exactly one terminal `@<id> DONE ...` or `@<id> ERR <CODE>`. The host matches both responses to the request ID. A controller restart is announced as `!BOOT V=1`; that event invalidates all in-flight physical assumptions.

| Request | Terminal success | Meaning |
| --- | --- | --- |
| `HELLO` | `DONE HELLO V=1 CAPS=STATUS,HOME,REF,STOP,MAP,CARRY,CARRY_DIAG,CARRY_OFFSET,OFFSET,SAVE,GEOM,OVER20` | Negotiate version and the implemented commands; `CARRY_DIAG` permits grid-to-grid diagonal legs and `OVER20` advertises the delivery overshoot required by this host. |
| `STATUS` | `DONE STATUS REF=<0\|1> BUSY=<0\|1> MAP=<0\|1> SAVED=<0\|1>` | Read reference, busy, occupancy-map and saved-geometry state. |
| `HOME` | `DONE HOME` | Full X/Y calibration has actually completed. |
| `REF` | `DONE REF` | Saved-geometry MIN reference has actually completed. |
| `STOP` | `DONE STOP` | Both axes and magnet are stopped; reference is invalidated. An interrupted request receives `ERR CANCELED`. |
| `SAVE` | `DONE SAVE` | Store completed calibration geometry in EEPROM. |
| `GEOM` | `DONE GEOM X=... Y=... OX=... OY=... P=... I=... PPM=...` | Read live referenced geometry: X/Y travel, X/Y board origin, pitch, inset (millimeters), and pulses per millimeter, printed to four decimal places. |
| `MAP <bitmap>` | `DONE MAP` | Replace the compact occupancy guard from a physically reconciled position. |
| `CARRY <source> <destination> <points>` | `DONE CARRY` | Execute one validated, bounded carry and release the magnet. |
| `CARRY_OFFSET <source-square> <corner> <destination-square> <points>` | `DONE CARRY_OFFSET` | Pick up at a known in-square corner and carry directly to a vacant board square. |
| `OFFSET <square> <corner> <direction>` | `DONE OFFSET` | Carry a piece within its occupied square, without changing the occupancy bitmap. |

Other errors include `BUSY`, `SYNTAX`, `UNKNOWN`, `DUPLICATE`, `REFERENCE`, `MAP`, `ROUTE`, `CAL_X`, `CAL_Y`, `GEOMETRY`, and `MOTION`. A command that times out, sees a reboot, or receives an unrelated/malformed terminal response enters an **uncertain** state. `GEOMETRY` from `CARRY` or `CARRY_OFFSET` also requires reconciliation because it can report an invalid live carriage position. The computer must stop and reconcile before committing or resuming a physical action. A repeated ID while still pending may receive its ACK again; a completed ID must not be replayed as a new motion request. IDs increase without wrapping during one boot, with `65535` reserved for a final emergency `STOP`.

## Carry and occupancy encoding

`MAP` takes exactly 24 uppercase hexadecimal characters (12 bytes). Within each byte, the least significant bit is the lowest position ID. IDs `0..63` are `a1..h8` in rank-major order; IDs `64..95` are perimeter slots `P00..P31`. The initial chess position with all parking slots empty is `FFFF00000000FFFF00000000`. The host sends this command only after the physical board and host inventory have been reconciled. The bitmap records occupancy, not piece identity.

`CARRY` names source and destination as decimal position IDs `0..95`. `<points>` is 4 to 24 characters: two base-17 characters per waypoint, inclusive of pickup and delivery, for **2..12 waypoints**. Digits `0..9` and letters `A..G` encode a half-square coordinate `0..16`; each pair is `(x,y)`. For example, `79` is the center of `d5`, and `00` is parking slot `P00`. Square centers are odd/odd; grid intersections and parking positions are even/even. Center-to-grid links are one-step diagonals; grid-to-grid legs may be orthogonal or 45-degree diagonal. The host plans the route from a current occupancy snapshot, checking measured piece clearance and the expected positions of any pieces temporarily offset within their squares. For ordinary moves, a configured tight-route retry cannot override a modeled clearance violation. Castling alone may use a last-resort override after every checked plan fails; the rook nudge, occupied-center and travel checks, waypoint cap, offset pickup, and release clearance remain enforced. The firmware checks route topology, map occupancy, and travel bounds before energizing the magnet. It rejects a route that cannot fit in 12 waypoints; neither side truncates one.

`OFFSET` names a board square ID `0..63`, a corner `NW`, `NE`, `SW`, or `SE` (X decreases/increases for W/E; Y increases/decreases for N/S), and direction `OUT` or `IN`. The corner target lies **inside that square**, 0.30 board pitch from its center on each axis; it is not a perimeter parking position. `OUT` picks up at the square center and drops at the corner. `IN` picks up at that same corner and returns to center. For example, `OFFSET 7 NE OUT` nudges a rook from h1 toward its outer-file, inward-rank corner. The same command can temporarily nudge another standing piece when the host plans a crowded carry. Each command waits for magnet release, travels to pickup with the magnet off, performs the short loaded move, releases, and returns `DONE OFFSET`. The firmware requires a referenced board and an occupied source bit, verifies both endpoints against measured travel bounds, and rejects the segment when another occupied square or parking center comes within the configured 18 mm piece diameter. The bitmap remains unchanged, so the host checkpoints each active offset and checks later motion against the commanded corner positions. The firmware cannot sense whether the piece actually followed the magnet.

`CARRY_OFFSET` is used after a confirmed `OFFSET ... OUT` at the same source and corner. Both IDs must be board squares `0..63`; the destination must be vacant in the firmware map. Its `<points>` uses the same 2..12 encoded waypoints as `CARRY`: the first pair names the source **center** and the last pair the destination center. The first pair is an encoding anchor only. The carriage travels with the magnet off to the known 0.30-pitch corner, picks up there, and carries directly to the second encoded waypoint, without a separate `OFFSET ... IN` leg. The remaining legs follow the encoded route. Before any motion, firmware validates the normal route topology, map and travel bounds, the corner bounds, and 18 mm clearance from occupied centers along the actual first loaded leg. Its occupancy bitmap moves the source bit to the destination bit only on `DONE CARRY_OFFSET`; an interrupted carry invalidates the map and reference. There are no sensors to verify that the rook actually reached its corner, so the host must checkpoint `OFFSET ... OUT`, the king `CARRY`, and `CARRY_OFFSET` separately and reconcile any uncertain step before continuing.

For a `CARRY` or `CARRY_OFFSET` ending on a board square, and for `OFFSET OUT` and `OFFSET IN`, the magnet stays on beyond the nominal endpoint in the direction of the final loaded segment. It first tries **0.20 board pitch** (6.25 mm at 31.25 mm pitch). If that pulse target exceeds measured travel bounds, it tries 90% of that extension (0.18 pitch, 5.625 mm); if that also exceeds bounds, the command fails before motion. A `CARRY` ending at perimeter parking releases at the nominal slot with no extension. The encoded waypoints, square or corner named by the request, and `MAP` update remain nominal; the release point is computed from measured geometry and is not another wire waypoint. The host mirrors the bounded retry and preflights the extended loaded segment against measured bounds, nominal occupancy, and any known offset piece positions. Firmware checks the release pulse target against measured bounds and the extended segment against occupied centers in its nominal `MAP`, as well as checking the encoded route. The host additionally checks displaced-piece positions and its configured clearance model. The extension aims to compensate for a piece lagging behind the magnet; open-loop motion and the lack of piece sensors mean `DONE` does not establish that the piece actually stopped at the nominal square center or corner. Inspect delivery and adjust calibration only from physical trials.

After `HOME` or `REF`, the host reads `GEOM` and uses those numbers for checked route planning. The four-decimal reply has finite precision; the clearance margin must allow for that rounding, motor path error, and physical centering error. `GEOM` returns `ERR REFERENCE` before a live reference exists. `HELLO` and `GEOM` return `ERR BUSY` during motion or calibration so their longer replies cannot delay limit sampling.

During a board move, a limit input must remain closed for 3 ms before it stops both axes. Switch activity while idle or between movement segments is ignored. Homing still uses the first raw switch edge followed by stationary confirmation. A sustained limit trip during a carry stops motion and makes the physical position and map uncertain.

`DONE` confirms commanded steps and the release sequence. It does **not** prove physical pickup or delivery; there are no piece-presence sensors in the imported hardware. After a stop, reset, fault or timeout, the live carriage and board map need physical reconciliation.
